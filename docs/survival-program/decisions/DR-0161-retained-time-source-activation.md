# DR-0161 — retained mailbox time-source activation

Date: 2026-10-21. Owner: Mr. X. Status: accepted bounded source/activation scope;
matching executable and connected qualification remain separate.

DR-0160's additive DTS1 successor also advances paired XNA1 and rebinds the
operational closure. It must not run the pre-mailbox installation ceremony on
an enrolled mailbox contour. The older guard remains mandatory.

An explicit current-dev maintenance flight uses the existing full offline
operational renewal and its sealed activation plan. No additional protocol
author or wire format is introduced. DTS1 changes are additive: every old tuple,
radius, quorum, sample age and width stays unchanged. Fresh current/next TLS
pins and traffic keys are required by ordinary operational succession. Registered
node identities, genesis, offline CA key, accounts and native journals remain.
Installed SANs and CRL distribution extensions survive fresh leaf-key rotation;
the signed CRL advances its number while preserving revocations. The expired or
nearly expired operational horizon is renewed by explicit offline root approval,
never by extending old proofs, changing the clock or skipping currentness.

Mailbox issuers rotate independently to fresh role-separated keys with an
advanced minimum grant generation. Old issuer grants cannot regain current
authority under a new empty revocation namespace. New SQL revocation roots
are appended explicitly, preserving the network grant journal, every old scope,
signed/pending snapshot, serial and counter. No runtime DDL, reset or upsert.

All affected writers stop before installation. A sealed bounded whitelist and
authenticated before-images bind exact candidate and predecessor; only the
publisher's existing mutation owner imports its HMAC journal and publishes the
complete signed prefix. Neither offline root nor the complete private candidate
is mounted into an online service. Only the exact new role seed reaches each
isolated signer volume. A failed mixed-generation install remains stopped.

Node policy succession is an explicit listener-free command. It verifies the
exact signed predecessor, both actual protected old role floors and their
signatures, new current host, fresh issuer keys and the greater grant floor.
It enrolls only genuinely new policy-scoped MGR custody, retaining old scopes
and the original key ring. It must reauthenticate the actual existing native
operation/replay/mutation owners; initial native enrollment is forbidden.
Missing/split old or new protected roots fail closed, never get reconstructed.
Ordinary startup cannot call this ceremony or auto-enroll a policy.

New root approval is not client delivery evidence. Qualification requires hostile
predecessor/key/horizon/input tests, preservation across native cold reopen,
retained installation and fresh proofs naming the new policy, then the same
three CLI accounts/history without reset. Provider availability, first-attempt
delivery and latency are measured, never inferred from the source list alone.
